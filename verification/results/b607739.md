## Failing rows

### E3 and E14 — wrong JSON type in a reset fixture answers 422 instead of 400

Requirement, `spec/stage-1.md` §5:

> | 400 | `malformed_request` | Unparseable body, or a field of the wrong JSON type |
>
> A field of the correct JSON type with an invalid format or out-of-range value gives
> 422 `validation_failed` …
>
> Reserve 400 `malformed_request` for a body that does not parse or a field of the wrong type.

`POST /_test/reset` (§3.3) does not name any error code of its own, so §5 governs it.

Command (against the `b607739` image):

```
for body in '{"restaurants":7}' '{"users":"ada"}' '{"reservations":3}' '{"restaurants":[7]}' \
            '{"restaurants":[{"id":"r","name":"n","timezone":"Europe/Berlin","slot_minutes":30,"reservation_duration_minutes":90,"cancellation_cutoff_minutes":120,"tables":[{"id":"t_1","label":"1","capacity":4}],"opening_hours":[{"weekday":"thu","opens":"18:00","closes":"22:00"}],"tables":7}]}'
do
  curl -s -w ' %{http_code}\n' -X POST localhost:8080/_test/reset \
    -H 'content-type: application/json' -d "$body"
done
```

Expected: `400` with `{"error":{"code":"malformed_request", …}}` — each of these fields has the
wrong JSON type, which §5 assigns to 400, in contrast to a correctly typed field holding an
invalid value.

Actual, all five cases:

```
422 {"error":{"code":"validation_failed","message":"restaurants must be an array"}}
422 {"error":{"code":"validation_failed","message":"users must be an array"}}
422 {"error":{"code":"validation_failed","message":"reservations must be an array"}}
422 {"error":{"code":"validation_failed","message":"restaurant must be an object"}}
422 {"error":{"code":"validation_failed","message":"tables must be an array"}}
```

Every other 400 case the suite exercised is correct: an unparseable body on any endpoint gives
`400 malformed_request`, a missing `Idempotency-Key` gives `400 missing_idempotency_key`, and
`POST /_test/import` follows §10 exactly (unparseable → 400; missing `state`, wrong `track`,
`format_version: 2`, `state: "text"` → 422 `validation_failed`, destination untouched).

Spot check against the current result-repo head `ad00f9b`: the same five reset bodies still
answer `422 validation_failed`, so this is not something the four newer commits fixed.
