## Still defective

### D1 — a fixture may not declare `cancellation_cutoff_minutes` of 0 (O1, Q1)

`POST /_test/reset` answers `422 {"error":{"code":"validation_failed","message":"restaurant
r_anker cancellation_cutoff_minutes must be a positive whole number of minutes"}}` for `0`.
The same value through `POST /_test/import` answers `204` and reads back as `0`.

Violated sentence, §5 lines 169–171: "A field of the correct JSON type with an invalid format or
out-of-range value gives 422 `validation_failed` … This includes invalid dates, negative counts
and values exceeding a stated maximum or length." No maximum or minimum for
`cancellation_cutoff_minutes` is stated anywhere in stage-1.md: §4 line 103 gives only its
meaning, §3.3 states no fixture constraint beyond §4 and §3.4, and the document's only numeric
limits are `party_size` below 1 (line 352) and `Idempotency-Key` 1 to 255 (lines 182, 233). Zero
is a whole number of minutes, not a negative count and not over any stated maximum, so the floor
the fixture validator invents has no basis in the specification.

The neighbouring edges behave correctly and are unaffected: `-1` and `-30` answer
`422 validation_failed` (§5's "negative counts"), the string `"0"` answers `400 malformed_request`
(§5 line 177), `10080` and `604800` answer 204, and with a cutoff of 0 actually installed the
arithmetic is right — a booking starting exactly now cancels `409 cutoff_passed`, one starting in
an hour cancels `200 cancelled`, one that already started gives `409 cutoff_passed`. So nothing
downstream needs the refusal; it is a validator artefact, and it is the only place in the service
where two test endpoints disagree about the same field value.

### D2 — import installs states carrying impossible local times (O5, O6, Q2)

`POST /_test/import` answers `204` and changes the destination when one reservation's
`starts_at_local` is `"2026-02-30T19:00"`, `"2026-12-10T25:00"`, `"2026-12-10T19:00:00Z"` or
`"not a date"`. The paired probe puts the identical value through both test endpoints: seeded
through `/_test/reset` the same `2026-02-30T19:00` answers `422 validation_failed`, carried into
`/_test/import` it answers `204`, and afterwards the destination holds `2026-02-30T19:00` while
`GET /reservations/{reference}` answers `200` with `starts_at "2026-12-10T19:00:00+01:00"` left
over from the booking it replaced.

Violated sentence, §10: "Invalid JSON follows §5; missing fields, wrong track/version or an
invalid state give 422 `validation_failed` without changing the destination." The state it
installs is invalid by §5's own field rule, which fixes the only valid form of `starts_at_local`
as a bare local `YYYY-MM-DDTHH:MM` and lists invalid dates among the 422 cases; the service
already enforces exactly that on the fixture path, so import is the only door that skips it.

The "accepted unchanged" guarantee does not cover these states: it is scoped to "an unchanged
export produced by this service", and no booking path can produce a reservation whose local time
is impossible, so refusing them costs nothing and holds for every later stage that must import
stage-1 exports.
