## Retraction: Q11 and Q23 failed against my probe, not the product

I reported `Q11` and `Q23` as failing at `677872b` and `fc5f126`, twice, with identical numbers:
"the page held 261 elements, 0 of them new against the settled page". Those numbers were wrong,
and the same wrong numbers appearing before and after a real fix is what gave the game away.

The probe held the response with `time.sleep(1.6)` inside a Playwright route handler. Route
handlers run on the same thread the sync API uses for every page call, so the sleep blocked my own
`wait_for_timeout(700)` and the "during" snapshot could not execute until the held response had
been delivered and the app had rendered the settled page. The row measured the settled page and
called it the waiting one. `renderLoading` existed before `d2666b8` too; my probe never saw it.

The fix delays the answer inside the page, so the driver stays free to sample: hold the promise
`window.fetch` returns for the next `/availability` call. Everything else in the row is unchanged.

**This is why Q11 and Q23 are the only two rows I am retracting, and it also means the earlier
`677872b` and `fc5f126` reports overstated the failures.** Both reports are on record with the
wording they used.

## Retraction: U1 and U2 were passing for the wrong reason

`recovery.py` held its first answer with `time.sleep(2.5)` inside a route handler too. The same
serialisation meant the second, five-cover search could not be issued until the first had already
been delivered, so the two answers never crossed and the stale-overwrite hazard was never in play.
Both rows passed without testing anything. They now delay inside the page: the first answer is
held 2.5 s, the second is issued 0.3 s later and lands first, and the grid holds 44 cells
available with no stale overwrite. The conclusion is the same, but it is now earned.

## The upgrade path is broken: Y1 fails

`verification/probes/s2/upgrade.py`, new. Stage-1 built from the same commit, served on 8081;
stage-2 from this commit on 8080.

**Y1 fails.** A stage-1 export imports with 204 and every exported row reads back out of stage 2
unchanged: 2 users, 1 token, 1 reservation, 1 receipt, no row lost and none added, counters
identical. Then the upgraded service answers **422 `validation_failed` for
`/availability?restaurant_id=r_anker&date=...&party_size=2`**, for every party size and every date.

The container log names the cause:

```
[tablekeeper] unexpected failure: TypeError: restaurant.combinable is not iterable
    at Object.availability [as handler] (/srv/tablekeeper/src/routes.js:195:35)
```

Reproduction, three commands:

1. `POST /_test/reset` on stage 1 with the same fixture minus `combinable`; `GET /_test/export`
   on stage 1 returns a restaurant record with keys `cancellation_cutoff_minutes, id, name,
   opening_hours, reservation_duration_minutes, slot_minutes, tables, timezone` and no
   `combinable`. This is not a malformed export: it is exactly what a stage-1 service emits.
2. `POST /_test/import` on stage 2 answers 204. `GET /restaurants` and `GET /restaurants/r_anker`
   both answer 200 on the imported data.
3. `GET /availability` answers 422, before and after, for party sizes 2 and 4.

**Why.** `stage-2/src/model.js:189` reads `combinable` as optional and returns `[]` when it is
absent, and the comment above it says so outright: "Absent means no declared pairs, which is what
every stage-1 fixture says by omission and is the only reading under which a stage-2 service can
accept a stage-1 export." That default only runs in `normalizeRestaurants`, on the fixture path.
`transfer.js:152` stores the imported state as given, so the stored restaurant keeps no
`combinable` key at all, and `routes.js:195` iterates it directly. The default the code documents
is never applied on the path it was written for.

Two defects in one. The iteration assumes a field the import path does not guarantee, and the
resulting `TypeError` is reported to the client as `422 validation_failed` rather than as a
server fault, which is why the symptom reads as a bad request instead of a broken service.

**Severity.** After a legitimate upgrade the service answers 422 for every availability query, so
no diner can search and nothing can be booked. The rows that pass below do so because they use
paths that do not touch `availability`.

**Owner.** Builder: `stage-2/src`. Either normalise on read, or normalise the state on import so
the documented default applies. Worth deciding separately whether an internal `TypeError` should
surface as 422 at all.
