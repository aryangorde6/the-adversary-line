## Sabotage triage: the two mutants the probes missed

Full write-up in `verification/sabotage-triage-aa4382f.md`. Summary:

- **Mutant 11 is a real gap and is now closed**, but not on the row the sabotage report named.
  The mutant throws a bare `Error`, which `server.js:117` maps to **422 `validation_failed`**,
  so `E16` (which counts answers `>= 500`) could never see it, and `C1` only called `/health`
  a handful of times. Measured: 400 sequential calls give `200x363, 422x37`. Two new rows,
  **C1b** (400 sequential calls, every status and body recorded; a defect failing a share `p`
  of calls is missed with probability `(1-p)^400`) and **C1c** (50 in flight at once). Both
  pass on `aa4382f`, both fail on mutant 11. `/health` is a per-request contract and a flaky
  answer breaks it regardless of whether the failure is a 5xx.
- **Mutant 3 is an equivalent mutant and is not catchable.** The only `await` in the request
  path is `prepare` at `server.js:169`, which runs before the lock is taken; every handler
  inside the lock is synchronous (`domain`, `model`, `moves`, `transfer`, `time` contain no
  `await`, and the three in `routes.js` are all in `prepare`). A synchronous critical section
  cannot interleave on one Node thread, so `fn()` and `lockTail.then(fn, fn)` are
  observationally identical. The mutex becomes load-bearing only if a handler grows an
  `await`. **D10b** was added regardless: 6 rounds of 50 *mixed* in-flight requests with INV1
  and partial state read back from the service, because the original D10 was a single round
  of 50 identical requests and only fails if the race window lines up once.
