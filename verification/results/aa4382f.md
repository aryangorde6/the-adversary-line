### Mutant 15, the cutoff boundary — caught in process, and not over HTTP

`P33b` and `P33c` in `probes/cutoff-boundary.mjs`.

The mutation is `now + cutoff*60000 > starts_instant` where the ruling is `>=`. `starts_at` is always
a whole local minute, so `now + cutoff*60000 == starts_instant` holds only when the service's own
clock lands on that exact millisecond. No client can choose it, so **no HTTP probe can discriminate
this mutant** — `P33c` passes on both implementations, which is the measurement, not a gap. `P33b`
asks the exported `cutoffReached` directly at three instants around the boundary instead.

| Service | P33b (in process) | P33c (over HTTP) |
| --- | --- | --- |
| `aa4382f` | PASS — cutoff 0 and cutoff 120 refuse on the boundary, one millisecond later refuse, one millisecond earlier do not | PASS |
| mutant, `>` for `>=` | **FAIL** — at the boundary `false`, one millisecond later `true` | **PASS**, as predicted |

This corrects the premise in the ruling that two probes would close it. One row closes it, and it
has to be in process. `P33c` is kept because it pins the rule where a client can actually reach it,
with cutoffs derived from the clock at the moment of the call and the distance measured again
immediately before each cancel, so a minute rolling over is reported rather than turned into a wrong
expectation.

The probe bugs I hit writing it, since they would bite anyone repeating this: `starts_at_local` must
be `YYYY-MM-DDTHH:MM` with no seconds; a start derived from a UTC clock has to be written in the
restaurant's own local time or the arithmetic and the booking land on different minutes; a
`cancellation_cutoff_minutes` derived from a rounded distance can leave the start outside the window
and turn a correct service into an apparent miss; and two bookings an hour apart on the same table
overlap at the default 120-minute duration, so the pair needs two tables.
